# Role application periods and archetype skills

Roles have an optional `application_closing_date`, editable in role metadata for both source captures and legacy JSON imports. JSON and raw/PDF ingestion also accept this field. If blank, the effective closing date is four calendar months after the posting date, clamped to the last day of the destination month. If the posting date is unknown, the original role `created_at` date is used. Source dates remain intact; the API exposes `effective_posting_date`, `effective_closing_date` and assumption flags separately.

The closing day is inclusive in Europe/Dublin. `/api/roles?period=current` (also `live`) returns open roles; `historic` returns closed roles. Explicit posting-year/date filters retain their existing precedence. The default Opportunities view shows live roles; all dates and historic roles remain available. Application creation and reopening a closed/withdrawn application are guarded on the server. Existing active application workspaces and their history stay accessible after the role closes.

Capability coverage (`/coverage`) now includes a typical-role selector and spider chart. Each archetype can save three to eight distinct active vocabulary concepts as its target skillset. Until saved, suggestions are the eight most frequently required concepts from assigned observed postings, counting each posting once per concept and using the canonical reviewed requirement loader. Historic postings contribute to the archetype sample. Suggestions are labelled, never silently persisted. Skills may also be selected from the active vocabulary when the archetype has few or no assigned postings.

The chart reuses current capability derivation and atomic concept evidence. Its scale is the existing evidence scale: evidenced 100, partial 50, asserted 25, no evidence found 0. Every selected skill's target is full evidence (100). This is not a proficiency rating or a claim that missing evidence means missing ability. Unconfigured capability assessments are shown as unavailable and suppress the chart rather than becoming false zeros. Deprecated saved skills produce a replacement notice. A table retains full labels and statuses; narrow screens use numbered axes.

The new backend migration adds nullable columns to existing tables, without backfilling source dates or changing RLS. The normal backend migration runner applies it before the new code is used. No production migration was run during implementation.

Validation includes date-boundary and application-guard unit tests, existing frontend regressions, chart selection/save tests, and a Playwright desktop/mobile chart workflow. A disposable PGlite PostgreSQL engine also verified the migration, array-size constraint, actual requirement aggregation and save queries, Python/SQL date parity, and application insert/idempotency/deadline rejection. The normal PostgreSQL integration suite requires a local `TEST_DATABASE_URL`; those tests skip when that server is unavailable.
